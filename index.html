the shape this branch adds
what's actually new

MeshCore already has an ESP‑NOW repeater‑to‑repeater bridge. This branch doesn't reinvent that — it adds the three pieces that make a Trifecta node possible, plus a new way for a companion to skip LoRa entirely.

PieceStatus
ESP‑NOW bridge, repeater ↔ repeateralready in MeshCore
IP bridge — WiFi + DTLS, repeater ↔ repeater or site ↔ site over any IP networknew, this branch
Running multiple bridges at once on one repeater ("Trifecta")new, this branch
Companion with no LoRa radio, joining purely over ESP‑NOWnew, this branch

That last one is the one worth pausing on: a companion board like a Waveshare ESP32‑S3‑Zero can join a Trifecta repeater's ESP‑NOW side‑channel as its primary radio — no LoRa chip, no LoRa airtime used, no LoRa collisions contributed. It just shows up as another node on the mesh.

use cases
01

Keep small devices off LoRa entirely

A well-placed repeater handles the real LoRa mesh; nearby companions that don't need LoRa range — a desk node, a phone-adjacent client, a sensor — join over ESP‑NOW instead. They stop consuming LoRa airtime and stop contributing to collisions, without losing mesh connectivity.

companion (no LoRa) --ESP-NOW--> Trifecta repeater --LoRa--> rest of mesh
02

Get the repeater itself deep into a building

This one isn't about getting companions off LoRa — it's about the repeater's own backhaul. Place a Trifecta repeater wherever WiFi or ethernet reaches, even somewhere LoRa can't escape the structure, and let it bridge back to the outside mesh over IP. Companions inside the building still reach it the normal way — LoRa (fine at indoor range) or ESP‑NOW.

indoor Trifecta repeater --IP/WiFi--> outside repeater --LoRa--> rest of mesh ↑ local companions join here over LoRa or ESP-NOW as usual
03

Seed a greenfield deployment

Drop a repeater into an area with no LoRa neighbours yet. It can't reach the main net on its own — but it can bridge to another Trifecta repeater over another available IP link right away, so it's useful from day one. As more local repeaters go up around it and start hearing each other over real LoRa, the IP link quietly becomes redundant instead of load-bearing.

new area, no LoRa neighbours yet seed repeater --IP link--> established Trifecta repeater (later: local repeaters link up over LoRa; the IP hop becomes optional)
04

Link sites without touching any outside IP network

Same IP bridge, entirely different transport: an organization with two buildings can link them over a private LAN or VPN, or over their own point‑to‑point radio (microwave, 60 GHz, whatever they've already got) — no port forwarding, no outside IP network exposure at all, just one unified mesh across sites.

building A Trifecta repeater --IP link--> building B Trifecta repeater
on trusting what's on the other end of an IP link

Most of the use cases above don't touch any outside IP network at all — but for the ones that do, it's worth stating plainly, since it's a natural first question.

It's an intentional point-to-point link, not a public portal

  • Nothing changes for a LoRa-only node. The bridge only exists on repeaters that explicitly enable it.
  • The IP hop is authenticated and encrypted with real DTLS — the same audited TLS machinery (mbedTLS) HTTPS runs on, over UDP, using a pre-shared key.
  • It's exactly two fixed peers per link. There's no mode where it accepts connections from anyone who doesn't already have the key.
limitations
32

ESP32 boards only

Both ESP‑NOW and the IP bridge (WiFi + mbedTLS) are Espressif-specific. Nothing here touches nRF52, RP2040, or STM32 boards.

RF

ESP-NOW and WiFi share one radio, one fixed channel

On a Trifecta repeater, ESP‑NOW and the IP bridge's WiFi connection have to agree on one static channel — no auto-hopping APs. We've run this combination successfully in our own testing, but haven't stress-tested it across a wide range of routers yet.

NAT

Port forwarding — but only on one side

Only the server side of an IP bridge link needs one UDP port forwarded. The other side dials out and works behind any standard NAT with zero config. If your server-side ISP uses CGNAT, port forwarding won't be possible there — you'd need a small VPS or similar instead.

git

This is a personal fork, not upstream MeshCore

Nothing here has been merged or reviewed by the MeshCore maintainers. It's beta-stage, tested so far on Xiao S3 WIO and Heltec V3/V4, and there are still open validation items in the design notes. The plan is to open a PR against upstream MeshCore once it's had enough real-world testing and validation to be worth proposing — that's exactly what this round of testing is for. In the meantime, treat every release here as a developer build for people willing to help shake it out — not something to put on a mesh anyone (including a future you) actually depends on. MeshCore itself is a volunteer, amateur-run project; this fork is several steps rawer than that.

changelog — beta 2

Repeater firmware only this round (Xiao S3 WIO, Heltec V3, Heltec V4 — V4 wasn't flashed to real hardware for this round, but shares the exact same radio driver and only touches shared, board-agnostic code, so it's included on that basis). No-LoRa companion assets are unchanged, still on the beta 1 release.

  • Fixed — a repeater no longer keys its LoRa radio for traffic that's only reachable over a bridge. Previously any reply or relayed message always broadcast over local RF and mirrored to the bridge, even when the destination had no radio at all (e.g. a companion reachable only through an ESP‑NOW/IP bridge chain). Covers both replies a repeater composes itself and ordinary message relaying through it — always falls back to broadcasting both ways whenever it isn't confidently sure, so this never risks silent delivery failures.
  • Fixed — a routing edge case where an internal "this came from a bridge" flag could, in rare timing windows, misapply to an unrelated later packet. Found and fixed during beta testing.
  • New — neighbors.all CLI command, merging RF-heard and bridge-heard neighbours into one list with a via column, without changing the existing neighbors command's output.
  • New — an IP-bridge path-return delay: when a repeater has a live RF neighbour, it briefly holds back mirroring a learned-path packet over the IP bridge, giving a genuine RF path a head start instead of letting the IP link win a route race it shouldn't.
  • New — NTP-based clock sync for boards with no battery-backed RTC.
  • New tool — watch_boards.py, attached to this release: auto-connects to every attached board's serial port at once and streams live, color-coded, multi-board debug output in one terminal, with payload-type annotation, advert name/coordinate decoding, and the routing decisions above highlighted in their own colors. This release ships with debug logging left on specifically so this tool has something to show.
changelog — beta 3

Repeater firmware only, same three boards as beta 2. No-LoRa companion assets are unchanged, still on the beta 1 release.

  • Fixed — a repeater's own broadcast traffic (adverts, flood replies) could get misrouted to a single bridge instead of reaching everyone. The heuristic that redirects a genuine reply straight back out the bridge it arrived from was also catching FLOOD-route sends and zero-hop self-adverts, both of which are meant to reach everyone, not bounce back to one peer. Found live: a repeater's own self-advert would silently fail to reach a peer repeater over the bridge whenever it happened to fire shortly after any unrelated bridge traffic. Fixed for both cases — always falls back to broadcasting to everyone whenever it isn't confidently a genuine reply.
  • New — the RF-preference delay from beta 2 (previously scoped to just the path-return reply) now covers first contact too: the first request, response, text message, or admin login between two new peers. Before this, first contact between two nodes had no RF-preference protection at all — the IP bridge could win the race for the very first exchange and get baked permanently into the learned route, even when a working RF path existed.
  • New — that delay now skips entirely when the destination is already confidently known to be reachable only over a bridge (e.g. an ESP‑NOW-only companion with no LoRa radio at all), so the two main use cases for this feature aren't taxed with pointless latency.
  • Changed — bridge-neighbour tracking now recognizes companions, not just other repeaters, which the fix above needs to actually detect a bridge-only companion as bridge-only. The stock, RF-only neighbors CLI table is unchanged. Table size now matches the RF-neighbour table instead of a fixed cap of 8.
changelog — beta 4

Repeater firmware only, same three boards. No-LoRa companion assets are unchanged, still on the beta 1 release.

  • Much better delivery reliability — for ESP‑NOW-only companions (e.g. the LoRa-less S3-Zero) with a marginal RF link to their paired repeater. Root-caused via live timing instrumentation: at normal desk range, some exchanges needed several retries to get a MAC-layer ACK back — a real RF margin issue, not a routing bug. The ESP-NOW send retry ceiling is raised from 4 to 12 attempts (with a matching timeout budget); each retry is cheap (~15–20ms), so a slower success now replaces what used to be a visible timeout error.
  • Fixed — the IP bridge's DTLS handshake could hang forever if the peer disappeared mid-handshake (network switch, IP address change), requiring a manual reboot to recover. Now times out after 30s and retries automatically, same as any other connection failure.
  • New — the IP bridge's heartbeat ping now defers by a tick when the ESP-NOW bridge has been active recently, on dual-bridge boards — avoids the heartbeat competing with an inbound ESP-NOW frame's ACK timing for the shared radio.
  • New — get bridge.channel now shows the radio's actual live WiFi channel alongside the configured value, flagging a mismatch explicitly.
  • watch_boards.py — new b hotkey dumps bridge status (WiFi/IP status, live channel) from every connected board at once; new c hotkey toggles watching companion boards too (skipped by default, since they speak a different protocol).
changelog — beta 5

Repeater firmware only, same three boards. No-LoRa companion assets are unchanged, still on the beta 1 release.

  • Changed — the IP bridge now runs over TCP+TLS-PSK instead of UDP+DTLS-PSK. UDP gave no delivery guarantee: a dropped datagram on the IP hop was silently invisible on both ends, indistinguishable from a failure anywhere else. TCP's own retransmit/ordering now covers that. The client-side connect is done with a manual non-blocking socket()/connect(), since mbedTLS has no non-blocking TCP variant — keeps the bridge's synchronous, single-threaded design intact, no new task added.
  • New — a new incoming connection can no longer preempt an active session just by connecting. It now has to complete its own TLS-PSK handshake, proving it holds the real shared secret, before it's allowed to replace the current peer. This also fixes a real issue found during testing: previously, if a peer's IP changed, the other side needed a manual reboot to accept the new connection; now a legitimately reconnecting peer gets back in automatically once it re-authenticates.
  • New — TCP-level keepalive (30s idle, 10s probe interval, 3 probes) as a backstop alongside the existing app-level ping/pong heartbeat.
  • Deployment note — if you reach a repeater through port-forwarding/DDNS for the IP bridge, the forwarded port now needs to allow TCP, not just UDP.
getting involved

Two waves, deliberately — starting narrow with boards we've already validated.

Wave 1 — now

You already have a Xiao S3 WIO or Heltec V3/V4

These are the boards this has actually run on as a Trifecta repeater. Everything's configurable from the standard MeshCore serial CLI — no custom tooling, no special client: 

$ pio run -e Xiao_S3_WIO_repeater_bridge_espnow_ip -t upload
set bridge.channel 11
set bridge.secret <your key>
set wifi.ssid <your ssid>
set wifi.pwd <your password>
set ip.host <peer host or IP>

Don't want to set up PlatformIO? Prebuilt binaries for Xiao S3 WIO, Heltec V3, and Heltec V4 are on the releases page — grab the plain .bin to upgrade an existing board (keeps identity/WiFi/bonds intact) or the -merged.bin for a blank one, flash with esptool.py, then configure with the same CLI commands above.

Optional — no-LoRa companion

Have a Waveshare ESP32-S3-Zero lying around?

This one's a companion with no LoRa radio at all — it joins a Trifecta repeater's ESP‑NOW side‑channel as its primary radio, so it uses zero LoRa airtime. Flash it the same way as a repeater (grab ESP32_S3_Zero_comp_radio_bridge_espnow_dual from the beta 1 releases page — unchanged since beta 1, so still there rather than on the newer repeater-firmware release — or build it yourself), then one extra step: there's no phone-app UI yet for its ESP‑NOW channel/secret, so it needs a small script (also attached to that release) to push them over USB: 

# find the port, then check/set its config
python3 set_bridge_params.py list
python3 set_bridge_params.py <port> get
python3 set_bridge_params.py <port> set 11 <your bridge secret>

Channel and secret have to exactly match what's already set on the repeater you want it to join (get bridge.channel / get bridge.secret on that repeater's own CLI). Applies immediately, no reboot. Needs Python 3 and pip install pyserial. Every other role — repeaters, and companions with their own LoRa radio talking to a Trifecta repeater normally — needs nothing extra at all.

Wave 2 — once we've shaken out the basics

Other ESP32 boards, broader testing

Building from source via PlatformIO for now. Prebuilt, flash-and-go images for more boards are on the list once wave 1 turns up anything that needs fixing first.
